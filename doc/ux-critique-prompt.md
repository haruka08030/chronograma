# UI/UX 批評ラウンド プロンプト

Chronograma の UI/UX を批評→修正するための再利用プロンプト。
`<<< >>>` で囲んだ部分を毎回書き換えて使う。

---

## 使い方

1. 下の「本体」をコピーして Claude Code に貼る
2. `<<<対象範囲>>>` を今回見たい画面に絞る（全体を一度に投げない。理由は末尾の注記）
3. 走らせる

---

## 本体（ここからコピー）

```
Chronograma（React + Zustand + Tailwind のタスク/時間管理アプリ）の UI/UX を批評し、修正してほしい。

### 対象範囲
<<<例: src/components/TaskList.tsx の一括操作バーと選択モード。
    ユーザーは「複数タスクを選んでまとめて処理する」ことをしたい。>>>

### 前提として先に読むもの（推測で批評しない）
- 対象コンポーネントの実際のコード
- src/locales/ja.ts と en.ts の該当キー（文言はここが正）
- 関連する src/store/taskStore.ts のアクション（その操作が可逆かどうかを確認する）
- 既存の類似 UI（同じ操作の単体版があるなら、その見た目・文言・確認ダイアログの有無）

### 評価ルーブリック（各 5 点 / 合計 50 点）
1. **発見可能性** — その機能があることに気づけるか。隠れた操作に頼っていないか
2. **操作コスト** — 目的達成までのクリック数・移動距離・持ち替え
3. **可逆性と安全性** — 破壊的操作の確認/取り消し。可逆な操作に過剰な確認を付けていないか
4. **フィードバック** — 操作の結果が即座に、正しい粒度で伝わるか
5. **状態の可視性** — 今どのモードか、何が選択されているか、何が起きたか
6. **一貫性** — 同種の操作が他画面と同じ見た目・語彙・挙動か
7. **文言** — 日英とも自然で、機能名でなくユーザーの意図の言葉になっているか
8. **視覚階層** — 主要動線と副次動線の重みが正しいか。危険な操作が目立ちすぎ/なさすぎないか
9. **モバイル/タッチ** — タップ標的サイズ、ホバー前提の操作、狭幅での折返し
10. **アクセシビリティ** — キーボード操作、フォーカス可視、aria、コントラスト

### 批評者（3 名、視点を固定して並行に立てる）
- **(a) 辛口の実ユーザー** — 毎日これを使って自分の時間を管理する人。「使い続けられるか」だけを見る
- **(b) デザインレビュアー** — 視覚階層・一貫性・文言・情報密度
- **(c) アクセシビリティ/モバイル監査役** — キーボード、スクリーンリーダー、狭幅、タッチ

> 3 名は必ず**別々の視点**を担当する。同じ指摘が 3 名から出たら、それは統合して 1 件として扱う（票数は重要度の証拠にならない）。

### 指摘の制約
- 1 名あたり**最大 7 件**、1 件**80 字以内**
- 各件に **severity（high/mid/low）** と **ルーブリック項目番号** を必ず付ける
- **修正後の具体案（どのファイルのどこを、どう変えるか）を含まない指摘は破棄**
- 「不十分」「わかりにくい」等の抽象批評は無効
- **コードを読んでいない推測の指摘は破棄。** 指摘には根拠となる file:line を付ける

### 修正の制約
- **high と mid のみ対応**。low は「見送った指摘」として最後に列挙のみ（次ラウンドに持ち越さない）
- 修正は該当箇所への**差分パッチのみ**。全文再生成を禁止
- 文言変更は必ず **ja / en 両方**を更新する
- 各ラウンドの修正後に `npx tsc --noEmit -p tsconfig.app.json` と `npm run build` を通す。通らない修正は撤回する

### 収束判定（いずれか成立で即終了）
- (a) 45 点以上 かつ 全項目 4 点以上
- (b) 2 ラウンド連続で改善が +1 点未満（飽和 → 打ち切り）
- (c) 3 ラウンド到達

### 各ラウンドの出力形式
1. **採点表** — 10 項目 × 点数 + 前ラウンド差分。合計点
2. **採用した指摘** — severity / 項目番号 / 根拠 file:line / 具体案
3. **適用した差分** — 実際に編集したファイルと変更内容
4. **検証結果** — tsc / build の結果（通らなかったものは正直に書く）
5. **見送った指摘（low）** — 一覧のみ
6. **収束判定** — どの条件で終了/継続か

### 最後に必ず報告すること
- **コードを読んでも判断できなかった項目**（実際に触らないと分からない体感・アニメーション・実機の見え方など）
- 点数は自己採点であり、実ユーザー検証の代わりにはならない旨
```

---

## 元の枠組みから変えた点と理由

- **批評者を 3 名に揃えた** — 元の指定は「3 名固定」と書きつつ (a)(b) の 2 名しか定義されていなかった。3 人目を埋めるにあたり、このアプリで最も抜けやすいアクセシビリティ/モバイルを担当させた
- **ルーブリックを定義した** — 「45 点以上/全項目 4 点以上」という判定基準に対して、項目そのものが未定義だった。10 項目 × 5 点 = 50 点満点で、45 点は「ほぼ全項目 4.5」に相当する厳しめの基準
- **「コードを読んでいない指摘は破棄」を追加** — LLM の批評で最も起きやすい失敗は、実物を見ずにもっともらしい一般論を並べること。file:line の根拠を必須にして塞いでいる
- **各ラウンドで tsc / build を通す制約を追加** — 批評ループは壊れたコードを積み上げやすい
- **ja/en 両方更新を明示** — この repo は文言が 2 ファイルに分かれていて、片方だけ直すと確実に落ちる

## 既知の限界（重要）

このプロンプトは**コードを読む批評**しかできない。この repo には Playwright/Puppeteer もテストフレームワークも入っていないため、批評者は**画面を見られない**。したがって実測が必要な項目（実際のコントラスト比、タップ標的の実寸、アニメーションの体感、実機での折返し）は原理的に**推測になる**。

精度を上げたい場合の選択肢:
- `npm run dev` で立ち上げて**スクリーンショットを自分で貼る**（最も費用対効果が高い）
- Playwright を入れて批評者に実際にスクリーンショットを撮らせる

## 対象範囲を絞る理由

「全体的に UI/UX が悪い」をそのまま投げると、批評は必ず浅く広くなる。1 画面 or 1 動線に絞ったほうが、同じ 3 ラウンドでも指摘が具体的になる。

絞り込みの候補（行数が多く、動線が複雑な順）:
- PlanVsActualView.tsx (1332 行) — 最も複雑
- TaskList.tsx (1244 行) — 選択モード、一括操作バー、セクション、DnD が同居
- HabitsView.tsx (848 行)
- TaskDetail.tsx (673 行)
- モバイル動線 — MobileBottomNav / TodoNavPanel / FloatingTimer
